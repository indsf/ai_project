# VMS 백엔드 설계 과제: S1 선박 의약품 재고 관리 시스템

## 1. 목표
해양법에 따라 선박에 의무적으로 비치해야 하는 의약품의 유효기한 관리, 사용량 추적, 재고 부족 감지를 처리하는 백엔드 서비스의 실행 계획(Spec)을 설계한다.

## 2. 필수 요구사항 (기능)
1. **약품 카탈로그 관리:** 약품의 마스터 정보(이름, 카테고리, 단위 등) 등록 및 조회.
2. **최소 비치 기준 관리:** 선박별로 특정 약품을 최소 몇 개 비치해야 하는지 설정 및 조회.
3. **재고 입고:** 로트번호, 수량, 유효기한을 기록하여 약품 입고 처리. (동일 약품도 입고 시점마다 유효기한이 다를 수 있음)
4. **약품 사용(출고) 기록:** 유효기한이 가장 가까운 약품부터 차감하는 FEFO(First-Expiry-First-Out) 방식 적용. 단일 사용 요청이 여러 입고 건에 걸쳐 차감될 수 있음.
5. **재고 현황 조회:** 선박별 약품의 현재 재고, 부족 여부(현재 재고 < 최소 기준), 유효기한 임박 항목 조회.
6. **사용 이력 조회:** 누가, 언제, 어떤 약품을, 얼마나 사용했는지 추적.

## 3. 제약 조건 (필수 준수)
- **기술 스택:** Java 또는 Kotlin, Spring Boot, PostgreSQL을 기준으로 설계한다.
- **제외 범위:** 다음 항목은 설계에 포함하지 않는다.
  - 발주/주문 관리 시스템
  - 비동기 처리 / 이벤트 버스 / 배치 작업
  - 선종별 필수 약품 목록 관리
  - 인증/인가 (단, 사용자 식별은 HTTP 요청 헤더의 `User-ID`로 전달된다고 가정. 예: `user1`)
- **결과물 제한:** 실제 코드는 작성하지 않으며, 산출물은 반드시 `spec.md`와 `decisions.md` 두 개로만 구성한다.

## 4. 심층 고민 및 정의 사항 (평가 핵심)
요구사항 중 모호한 부분은 스스로 정의하고, 아래 질문에 대한 해답과 트레이드오프를 `decisions.md`에 반드시 기록한다.
1. "선박의 최소 비치 기준" 정책 모델과 "물리적 창고 재고" 모델을 어떻게 분리하고 관계 맺을 것인가?
2. 약품 사용 기록 시 "아스피린 40정 사용" 외에, 어떤 입고 건(로트)에서 얼마나 차감되었는지 추적하기 위한 데이터 구조는 무엇인가?
3. 재고가 부족한 상태에서 사용 요청이 들어왔을 때의 예외 처리 전략(Edge Case)은 무엇인가?
4. 유효기한이 지난 약품에 대한 시스템적 처리 방식(조회 제한, 자동 폐기 등)은 어떻게 가져갈 것인가?
5. 동시 다발적인 약품 사용 요청 시 발생하는 재고 동시성 문제(음수 재고)를 방지하기 위한 트랜잭션/락(Lock) 제어 전략은 무엇인가?

## 5. 최종 산출물 (인수 조건)
- `spec.md`: 데이터 모델(ERD/DDL), API 설계(요청/응답 스키마), 비즈니스 로직(Pseudo-code), Edge Case 처리, Given-When-Then 테스트 케이스가 다른 개발자가 보고 즉시 구현할 수 있는 수준으로 구체적으로 작성되었는가?
- `decisions.md`: 설계 과정의 기술적 결정, 대안 비교, 선택 근거가 논리적으로 작성되었는가?
